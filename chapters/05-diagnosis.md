# Диагностика базы с устаревшими метриками

## Демонстрационный сценарий

Три метрики базы `demo-a` рассчитаны в 12:00 с TTL пять минут. Точка сбора продолжает отвечать, но к 12:06 обновлённых значений нет. Для примера считаем, что правило впервые зафиксировало все три просрочки в 12:06. При непрерывном выполнении условия предупреждение ожидается в 12:11. Расчёт восстанавливается в 12:14, и с этого момента снова выполняется по расписанию. Предупреждение снимается после выдержки восстановления, около 12:19. Конкретная секунда срабатывания зависит от расписания вычисления правила.

Table: Состояние метрик и оповещения по времени

| Время | Наблюдение | Ожидаемое состояние |
| :------------- | :------------------------------------- | :-------------------------------------- |
| 12:00 | Три метрики обновлены | Просрочек нет |
| 12:06 | `up = 1`, просрочены три разных показателя | Условие предупреждения выполнено, идёт выдержка |
| 12:11 | Просрочки сохраняются пять минут | Активно предупреждение базы |
| 12:14 | Расчёт обновил все три значения | Просрочек нет, идёт выдержка восстановления |
| 12:19 | Свежесть сохраняется | Предупреждение снято |

## Действия оператора

1. Выбрать нужную базу в Grafana и посмотреть `up` за тот же период, что и проблемные показатели. Если опрос неуспешен, начать с точки сбора и ошибки запроса.
2. При успешном опросе сравнить время последнего расчёта нескольких показателей. Если отметки остановились одновременно, проверить общее задание расчёта в 1С и его последние запуски.
3. Если расчёт идёт, а отстаёт только один прикладной процесс, перейти к диагностике его показателя. Для обмена открыть журнал соответствующего узла и направления. Для регламентного задания сверить последний запуск с расписанием и проверить результат выполнения.
4. После восстановления убедиться, что появилась новая отметка успешного расчёта, число просрочек снизилось и оповещение перешло в состояние восстановления.

Возраст метрик задаёт следующий диагностический шаг при успешном опросе. Если устарели несколько показателей с одним источником, проверка общего задания расчёта помогает быстрее локализовать сбой. Свежий показатель с проблемным значением направляет оператора к конкретному прикладному процессу.
